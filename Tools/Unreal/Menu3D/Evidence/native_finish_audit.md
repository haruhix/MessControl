## Findings to resolve before calling the menu finished

1. **Potential duplicate stage driver: verify compiled enable state before fixing.** Live WBP EventGraph has `K2Node_Event_2` (EventTick) exec output index 1 connected to `K2Node_CallFunction_174` (UpdateStage) input index 0. Live PC EventGraph has `K2Node_Event_1` (EventTick) exec output index 1 connected to `K2Node_MacroInstance_14` (IsValid), whose `Is Valid` output index 0 links `K2Node_CallFunction_35`; PC DSL identifies its UpdateStage call. WBP CDO `tickFrequency=Auto`. Both connected paths therefore exist and conflict with the documented single-PC owner. **Runtime duplicate execution is not yet proved:** ObjectTools exposes only errorMsg on these nodes; editor Python can find EnabledState but cannot read the protected property. The graph DSL/get_node_infos do not report node enabled state. Root should inspect enabled state/compiled behavior, then keep exactly the intended PC driver if both are enabled. Do not remove a deliberately disabled historical node based on DSL alone.

2. **Footer Back differs from Esc/inner Back.** Live `WBP_MainMenu3D:EventGraph.K2Node_ComponentBoundEvent_11` (OnClicked DaysBackButton) exec output index 1 links `K2Node_CallFunction_233` (ShowPage), whose Index input is literal `0`. Esc and inner collapse buttons use collapse first. Route footer Back through the same Back function to satisfy the stated collapse-then-Main behavior, with focus/pointer quiet state preserved. This is a graph finding, not a new runtime test.

3. **Inner Play opens a second complete main menu, not a finished connection screen.** Live OpenConnection guards Page1 / known selected day / matching active day / openness > .72, clears LegacyMenuHost, selects Page5, creates `/Script/MessControl.MCMainMenuWidget` and adds it. It does not pass SelectedDay. LaunchTitle stays `PLAY`; LaunchInfo says create/join. Native widget `NativeOnInitialized` immediately shows EPage::Main (MCMainMenuWidget.cpp:51–91), including Tutorial, Create Lobby, Join Lobby, Settings, Credits and Exit (234–242). This duplicates navigation and produces a visually separate 540×680 native card, opaque blue-black backdrop, different label/button styling (51–140). Proper connection UI must retain day context and use the same art direction.

4. **Day2/3 launch currently cannot mean Day2/3 gameplay.** Current native Host/Tutorial routes resolve only L_Mouth and L_Tutorial (MCMainMenuWidget.cpp:26–30, 474–495; MCSteamSessionSubsystem.cpp:140–152). Current AMCGameMode reads MCTutorial/MCLobby options, defaults FirstDayPlan to DA_Day01 and initializes its run from Day0; no selected menu day is passed in this route (MCGameMode.cpp:63, 77–82, 229, 388–405). Day2/3 artwork may be finished and openable, but launching the same day-one run under those labels would be misleading. Keep their gameplay action unavailable with an honest message until real day profiles/maps and a validated launch contract exist. Days4–7 remain Coming Soon with no launch.

5. **Startup and return still select the old front end.** Config/DefaultEngine.ini sets GameDefaultMap `/Game/Maps/L_MainMenu`. MCSteamSessionSubsystem::OpenMainMenu hardcodes that same map (277–281); AMCPlayerController::ReturnToMainMenu delegates to LeaveRoom and has the same fallback path (MCPlayerController.cpp:680–685). Changing only GameDefaultMap to v08 would leave Return to Menu on the old screen. AMCMainMenuPlayerController creates the old native widget and its own scene audio (MCMainMenuPlayerController.cpp:6–26). A new BP game mode/controller needs the intended existing audio behavior explicitly retained; it should not also spawn the old widget.

6. **The new settings screen is functional but incomplete compared with the existing one.** Current live WBP offers Low/High/Epic immediate Apply+Save and a Windowed/WindowedFullscreen toggle driven by bBorderless, with no initial synchronization from GameUserSettings, selection indicator or mode rollback. It lacks resolution and VSync controls and omits Medium/Cinematic/Custom. Existing native settings already implement actual settings reading, resolution/mode/quality/VSync and a 15-second display confirmation/revert including removal cleanup (MCMainMenuWidget.cpp:333–411, 428–456). Reuse the policy; do not regress it while reskinning. Replace the engine implementation copy `Настройки применяются к игре Unreal Engine.` with useful player-facing information.

7. **Credits/Exit need page-level finish checks.** Current new CreditsBody contains the game description and Unreal attribution, with no team/asset credits. Names cannot be invented; retain honest attribution content until supplied. Exit has Cancel and QuitGame wiring, but focus, Escape and visual hierarchy still require a short native page review. Main/Settings/Credits/Exit use the shared new shade palette; this audit did not render those screens and cannot certify final visual coherence.

8. **Nested Back/focus ownership needs an explicit contract.** Native MCMainMenuWidget consumes Esc/B in NativeOnPreviewKeyDown (459–467). At its EPage::Main, Back opens its own Exit page (485–489), while the outer Page5 Back clears LegacyMenuHost and returns to day select. A polished connection page should give its host a close/back signal at its root, restore focus to that day's Play button, preserve the selected mouth pose, and use internal Back only in nested host/join/video confirmation pages. Do not use widget-name scanning, button-array indices or reflected access to private controls as the production API.

## Minimum integration choices

**Asset-only scope, available now:** retain the existing native widget as an explicitly interim connection adapter; route Day1 to the existing real flow and show Day2/3 gameplay unavailable; fix footer Back and any confirmed duplicate driver; finish art and authored UI elsewhere. Settings can use GameUserSettings Blueprint APIs, but must explicitly implement/read current state and safe video confirmation. This can deliver an integrated visual preview, **not** a fully reskinned connection flow or selected-day gameplay.

**Recommended minimum proper C++ bridge for the requested finished menu:** expose a small intentional front-end API, preserving the existing session subsystem implementation. Either expose the subsystem's relevant host/find/join/state operations as BlueprintCallable/Pure with a state-change delegate for the authored connection screen, or add a focused connection-widget entry API plus root OnBackRequested and styling hooks. EMCMainMenuAction is currently a plain non-UENUM enum; HandleAction, ShowLobby/ShowPause/FocusMenu and session operations are non-UFUNCTION, and EPage/ShowPage/private controls are not a BP interface (MCMainMenuWidget.h:15–64; MCSteamSessionSubsystem.h:17–34). Existing AMCPlayerController::ReturnToMainMenu is already BlueprintCallable, but only covers the gameplay controller path. Do not call private methods through tree hacks or assume a native C++ method is a Blueprint node.

Keep this bridge narrow: known launch target, busy/error state, local/Steam existing behavior, and one root Back delegate. Add selected-day context to the connection heading; only enable real launch targets. Broad session rewrites, CommonUI migration or new day gameplay are not necessary for the visual finish. Reflection/API changes require supported UHT/editor compile handling; LiveCoding permission is not evidence that new reflected APIs have loaded successfully. Windows build/cook/package remains a separate unrequested task.

For startup/return, choose one consistent route **after the v08 finish is accepted**:

- Asset-only production identity: preserve the existing L_MainMenu as an explicit backup, then author the completed stage/BP game mode into `/Game/Maps/L_MainMenu`, retaining the original path used by startup/return. Keep the isolated v08 map for review. Audit old level behavior before replacing anything.
- Or keep a separate final map and update GameDefaultMap plus all return routes through one intended configuration/helper. Avoid scattered new hardcoded paths. Do not only change startup.

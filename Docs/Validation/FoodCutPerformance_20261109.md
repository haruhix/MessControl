# Нарезка винограда: кадр разреза, Draw и таймеры — 2026-11-09

Запрос: в Editor/PIE при нарезке винограда заметно растёт Draw time. Проверено
на текущих Editor-бинарниках и сохранённых данных, без изменения исходников,
runtime-ассетов, материала, коллизии или зачёта. Это диагностическая работа,
не оптимизация и не новый packaged benchmark.

## Подтверждённые результаты

Фикстура — настоящая строка `Bacon` из `DT_BreakfastMenu`, которая сейчас выбирает
`SM_GrapesPurple`, сохранённый scale 40 и реальные baked CollisionData. Целая
гроздь удержана неподвижной только для воспроизводимого контакта. Один обычный
удар ножом создал **47 частей: 9 готовых receipts и 38 остающихся физических
procedural-акторов**. Суммарно у постоянных частей 38 секций, 4 116 вершин,
5 910 треугольников; это не 38 полных копий исходной грозди на экране.

В кадре разреза native CSV зарегистрировал **793,661 мс GameThread** и
795,293 мс FrameTime. В Insights тяжёлое выполнение приходится на настоящий
таймер/работу персонажа в World Tick (~762 мс); отдельных пользовательских
trace scopes внутри алгоритма нарезки сейчас нет. Поэтому время каждой его
внутренней функции отдельно не выдается как измеренное.

Счётчики graphics draws/frame из финального trace, среднее с отбрасыванием
двух крайних GPU-frame значений в каждой фазе:

| Условие | Вызовы отрисовки |
|---|---:|
| До разреза | 366,24 |
| 38 физических частей видимы | 494,42 |
| Только CutVisual скрыты, физика сохранена | 366,39 |
| CutVisual снова видимы | 493,32 |
| Видимые части, физика выключена | 489,27 |

В этой сцене видимые куски добавили около 128 draws (~35%). Скрытие именно
мешей возвращает число почти к baseline; выключение физики не убирает
отрисовки видимых частей. Это подтверждает render-population cost, но счётчик
draws не является временем в миллисекундах.

Уникальный CPU scope `SceneRenderBuilder_Render` в RenderingThread:
baseline mean 3,949 мс → visible 4,497 мс → mesh-hidden 3,898 мс;
после восстановления 4,619 мс. Это участок CPU-подготовки сцены, не весь
показатель `stat unit Draw`. **Кратный рост Draw time на одной грозди в этом
прогоне не воспроизведён.** Сырой native CSV `RenderThreadTime` и его
CriticalPath почти всё время показывают ~0,001 мс в этом Editor-процессе;
они не используются как доказательство нулевой стоимости рендера.

## Что показал UI A/B

Три поздно созданных Screen-компонента действительно скрыты в UI-фазе;
до скрытия в ракурсе был только **один активный** индикатор. Graphics draws
493,32 → 489,32, Slate batches 44 → 40, Slate vertices примерно
21 210 → 20 864. После восстановления маркер мог уже уйти из видимой области.
Это не тест множества одновременно видимых таймеров и не доказательство,
что UI является главной причиной просадки пользователя.

Физические тела естественно засыпали во время последовательных окон:
в mesh-hidden awake count снижался 29 → 6, далее 4 → 1. Поэтому снижение
GameThread между такими окнами нельзя целиком приписывать скрытию меша,
отключению UI или только физике. Graphics draw-count A/B при этом остаётся
отдельным подтверждённым результатом.

## Что найдено в текущем коде

- Каждый постоянный остров получает отдельный зарегистрированный
  `UProceduralMeshComponent`; каждый непустой material section создаёт
  отдельные dynamic mesh batches по видам/проходам. Обычного StaticMesh
  instancing/LOD-пути у этих частей нет; геометрия извлекается из LOD0.
- У неготового ребёнка `FinishSpawning → BeginPlay → OnRep_Item` уже вызывает
  `BuildCutVisual`, затем `SpawnPortionActors` вызывает его ещё раз
  (`MCFoodCutPrototype.cpp:261–263`). Повторяются CPU-копирование/история
  разрезов/острова и convex/physics-state работа. Это подтверждённая по исходнику
  лишняя работа; конкретная доля этих функций в 794 мс отдельно не измерена.
- Перед cut convex ребёнок может временно зарегистрировать whole-source
  compound через `SetCollisionMesh`. Не следует предполагать, что каждый
  dirty-вызов обязательно создал отдельный render proxy: движок может их
  объединять в пределах кадра.
- `FilterIsland` уплотняет используемые вершины и bounds; исходный Static
  Visual скрыт, GripSurface скрыт/без теней. Двойная отрисовка static+procedural
  и сохранение полного исходного AABB в каждом острове не подтверждены.
- Готовые маленькие части — скрытые receipts без физики и отдельные Niagara-cue.
  Их нельзя считать телами с коллизией только по видимому полёту.

## Вариант с материалом для таймеров

В текущем UI есть CPU-генерация/raster контуров; кэш выбранного V2 contour
учитывает экранный transform и clip. Движущийся маркер способен его инвалидировать.
Одна material Image может убрать эту работу, сохранив Screen-space семантику,
но не убирает N виджетов/привязок/ресурсов автоматически. Уникальный MID на
каждый таймер также может мешать batching.

Общие instanced quads/shared material + per-instance data либо единый экранный
слой маркеров могут сократить саму популяцию отрисовок. При world-space варианте
потребуется сохранить нынешние размер в пикселях, billboard и отсутствие
world occlusion. Это предлагаемые варианты, не реализованные изменения.
Сначала нужен отдельный плотный UI-case, если целью становится именно он.

Первичные рекомендации Epic:
[UMG optimization](https://dev.epicgames.com/documentation/en-us/unreal-engine/optimization-guidelines-for-umg-in-unreal-engine),
[Widget Components](https://dev.epicgames.com/documentation/en-us/unreal-engine/widget-components-in-unreal-engine),
[ISM и Custom Data](https://dev.epicgames.com/documentation/en-us/unreal-engine/instanced-static-mesh-component-in-unreal-engine).
Стоимость material-only анимации не означает нулевую стоимость всего виджета
или его вызовов отрисовки.

## Уточнение: 45+ мс Draw именно в момент разлома

Пользователь уточнил: одно окно PIE, Draw доходил до 45+ мс, просадка возникала
при разломе винограда. Снята дополнительная короткая запись
`Followup45/Run_20261108T211323Z/`: baseline, затем три настоящих последовательных
разлома. Она уже завершилась к уточнению о transient-симптоме; новых прогонов
после этого не запускали. Основные релевантные фазы — baseline/cut_1/visible_1.

Первый разлом повторно дал **905,928 мс GameThread** / 905,531 мс FrameTime.
В следующих двух кадрах разлома maxima GT были 786,181 и 817,603 мс.
Это подтверждает воспроизводимый синхронный скачок в момент обработки ножа,
а не только накопление постоянных акторов после него. Счётчики первого разлома:
graphics draws 362,43 → 473,18 → 503,22; физические food-части 0 → 38.
Во время `cut_1` Slate batches остаются 40, vertices 20 864, как до удара;
увеличение видимых timer draw submissions как причина этого скачка не найдено.

Последующие 76/114 физических частей и семь phase exports оставлены вторичным
scaling-evidence; они не нужны для вывода о первом разломе. Глобальные Chaos
state-counters не отождествляются с числом food-акторов; отсутствие change-only
события в фазе не считается нулём.

Число 45 мс на самом `stat unit Draw` **не считается непосредственно
подтверждённым**: команда запрошена, но четырёх отложенных SWindow-снимков
панель не видна. Они показывают gameplay/куски, а не доказывают цифру Draw.
Отложенные снимки не ловят краткий пик по дизайну. Источник Draw в UE5.8 —
сглаженный global timing каждого PresentWindow, а не только scope
`SceneRenderBuilder_Render`; их нельзя напрямую сравнивать. Значение
`r.RenderThreadTimeIncludesDependentWaits` влияет на выбор critical-path waits.

# Технические решения для GDD 0.2

25 сентября 2026. Проектирование, **не отчёт о реализованных механиках**. Утверждённые правила и оставшиеся вопросы находятся в [GDD.md](GDD.md). Названия новых классов и DA ниже — предлагаемые, пока соответствующий шаг не отмечен выполненным в [журнале разработки](DevelopmentSteps.md). Шаг 1 уже подключает `DA_RunRules` к существующему забегу; остальные системы ниже остаются планом.

## 1. Основа данных

Рекомендуется сочетать Data Assets для составных определений с таблицей однотипных статусов. Значения, которые меняются во время забега, хранятся в реплицируемом состоянии акторов/компонентов и SaveGame. Общие DA не изменяются в процессе игры.

| Определение | Основные данные |
| --- | --- |
| `DA_RunRules` | Семь дней, начальное здоровье 100, восемь зубов арены, максимум четыре игрока, ссылки на расписание и правила завершения |
| `DA_ToolDefinition` | Тип действия, цикл стука 0,5 с, рабочая область, допустимые цели/статусы, анимация, звуки, параметры резки/захвата |
| `DT_StatusDefinitions` | ID, допустимые носители, способ снятия, число стуков, длительность, урон и его период, складывание, визуал и звук |
| `DA_FoodDefinition` | Модель/материалы, масса и коллизия, прочность/гниение, влияние при ударе, возможность захвата/резки, материал среза, последствия утилизации |
| `DA_BreakfastMenu` | Список продуктов со ссылками на Food DA, диапазоны количества, порядок и интервалы подачи, напиток |
| `DA_MenuRotation` | Допустимые меню, веса, дни доступности, ограничения повторов |
| `DA_EventDefinition` | Тип события, фазы, кривые силы/уровня, параметры подачи, статусы и последствия, длительность и ссылки на эффекты |
| `DA_DaySchedule` | Обязательные события, случайные пулы, меню завтрака, порядок/совместимость фаз, перерывы и черновой бюджет |
| Существующие DA анимации, физики и звуков | Сохраняются; новые события используют ссылки на них и именованные звуки |

Таблица статусов: кофе на зубе требует четыре стука. Статус может поддерживать игрока и зуб арены, но у каждого носителя свой экземпляр прогресса. Поддержка снятия статуса инструментом не означает автоматического разрешения самому игроку чистить себя — это отдельное правило.

DA удобны для редактирования ссылок на модели, материалы, кривые и наборы других DA. Это соответствует назначению [Data Assets в Unreal](https://dev.epicgames.com/documentation/en-us/unreal-engine/data-assets-in-unreal-engine). Численные балансовые данные при необходимости можно вынести в дополнительные Data Tables, сохранив один источник истины для каждого параметра.

### Ротация завтраков

Предложение: сервер формирует набор допустимых меню для дня, выбирает по весам из оставшихся в текущей ротации, затем пополняет набор после его исчерпания. Непосредственный повтор исключается, если есть другой допустимый вариант. Единственное доступное меню всё равно может выпасть. Для пустого пула задаётся явное резервное меню и диагностическое сообщение.

`RunSeed`, состояние генератора, история/остаток ротации и уже выбранные меню сохраняются. Клиенты получают выбранное меню и расписание подачи; самостоятельный random на каждом клиенте не используется. `FoodSpawnLane` хранит зоны появления над ареной и разрешённые области падения. Для завтраков со специальной темой дня можно назначить обязательное меню вместо случайного.

Редакторский сценарий: создать Food DA → собрать BreakfastMenu → включить в Rotation → указать Rotation в DaySchedule. Предлагаемый виджет проверки для хоста: выбрать seed/день/меню, просмотреть расписание и вручную запустить событие. Это инструмент разработки, не обязательное меню для обычного игрока.

## 2. Зубы как физический запас жизней

Предлагаемые сущности: `AMCToothAnchor` — зуб/посадочное место арены; `UMCStatusComponent` — статусы на зубе или персонаже; состояние забега в GameState и серверные операции в GameMode.

У каждого зуба арены постоянный `ToothId`. Состояния как минимум: доступен, зарезервирован для возрождения, потрачен, утрачен. Число доступных возрождений вычисляется по зубам, а не поддерживается независимым счётчиком, который может разойтись с ареной.

Серверная операция возрождения:

1. Проверить, что игрок действительно ожидает возрождения и операция ещё не выполнена.
2. Выбрать пригодный зуб и атомарно зарезервировать его.
3. Подготовить безопасное появление нового персонажа; способ переноса статусов определяется после решения вопроса в GDD.
4. При успешном появлении потратить зуб, обновить его место и передать управление. При техническом отказе появления вернуть резерв либо оставить операцию ожидающей — не терять зуб из-за ошибки спавна.
5. Реплицировать результат по ID; повтор запроса не расходует следующую жизнь.

Утрата зуба врагом/едой и расходование на возрождение — разные причины изменения состояния. Пустая лунка должна хранить причину, поскольку её урон и заживление ещё требуют отдельного правила. Захваты игроков, привязанные к исчезнувшему зубу, освобождаются.

## 3. Контактная чистка

Предлагается заменить универсальный `ApplyWork(DeltaSeconds)` для чистки на подтверждение цикла инструмента. Каждый цикл имеет ID; окно контакта привязано к анимации/процедурной фазе. Точный способ удержания контакта остаётся открытым в GDD.

Сервер проверяет владельца инструмента, состояние персонажа, допустимый темп, рабочую область, видимость цели и её активный статус. Один цикл даёт одной цели максимум один стук. Повторный сетевой пакет, несколько физических форм одного зуба и несколько callbacks не увеличивают счётчик. Если широкой щётке разрешено несколько целей, каждая проверяется отдельно.

Для кофе `CompletedContacts` меняется 0 → 1 → 2 → 3 → 4. После четвёртого подтверждения статус снимается один раз. Клиент может немедленно показывать движение инструмента, но степень очистки и завершение задачи определяет сервер. Прерывание сохраняет завершённые стуки; судьба незавершённого цикла требует решения. Величину прогресса клиент не присылает.

## 4. Разрезание, дробление и разрыв еды

**Процедурный разрез в месте инструмента возможен.** В UE 5.8 `Slice Procedural Mesh` разрезает ProceduralMeshComponent плоскостью, поддерживает создание второй половины, материала среза и обработку простой выпуклой коллизии. Это подтверждено [документацией Epic](https://dev.epicgames.com/documentation/unreal-engine/BlueprintAPI/Components/ProceduralMesh/SliceProceduralMesh) и исходником установленного движка `KismetProceduralMeshLibrary.cpp`.

### Хот-дог: разрез плоскостью

Предложение для первого варианта: замкнутая модель пищи с доступными вершинами, материалом внутреннего сечения и простыми выпуклыми коллайдерами. Во время успешного реза сервер определяет точку и нормаль плоскости по рабочей поверхности инструмента и его движению. Удар вне предмета или не пересекающая его плоскость не создают куски.

Один завершённый рез пересекает текущий кусок целиком по плоскости. Это ограничение первого алгоритма: произвольный кривой надрез, вырезание объёмного куска кончиком ножа и пластичная мякоть требуют более сложной геометрии. Положение и направление сечения при этом действительно соответствуют действию игрока.

Половины становятся отдельными физическими акторами со стабильными ID, собственными коллизией, массой, скоростью, гниением и точками захвата. Масса делится по объёму; стартовые скорости учитывают движение исходного тела. Захват перепривязывается к той части, где оказалась его точка. Встроенная функция создаёт вторую компоненту у прежнего владельца: для независимых сетевых предметов потребуется дополнительная логика акторов и состояния.

Нужны ограничения на минимальный размер куска, количество разрезов и физических фрагментов, а также бюджет обновления коллизии. Мелкая крошка может быть визуальным эффектом. При достижении предела игрок должен видеть, что кусок уже достаточно мал; операция не должна незаметно уничтожать оставшуюся еду. Пределы — параметры профиля пищи, числа определяются проверкой производительности.

### Тяга по надрезу

Предложение: надрез хранит положение, направление, глубину и остаточную прочность. Два захвата создают нагрузку; превышение порога в течение заданного времени завершает разрыв по выбранному надрезу. До этого допустима визуальная упругость. Полноценная деформация и разрушение мягкого объёма под любой тягой — отдельное исследование; готовый планарный slicer этого не обеспечивает.

### Орехи и хрупкие продукты

Для орехов подходит Geometry Collection с заранее подготовленными осколками и порогами разрушения. Стандартный процесс Chaos использует предварительно раздробленную геометрию и разрушаемые связи между частями; он не гарантирует новый точный срез по произвольному движению ножа. Основание — [Destruction Overview](https://dev.epicgames.com/documentation/unreal-engine/destruction-overview).

### Сеть разрезов

Предложение: сервер подтверждает операцию, назначает ID исходной части, версию геометрии, локальную плоскость и ID результатов. Клиенты воспроизводят визуальную геометрию из исходного ассета и упорядоченной истории разрезов; движение и столкновения игровых фрагментов определяет сервер. Позднему клиенту нужны снимок актуальных частей и история/данные их построения — одного разового multicast недостаточно.

Детерминизм геометрии на целевых сборках необходимо проверить. При расхождении нужна передача готового представления/снимка, а не предположение, что одинаковая команда всегда даёт идентичную геометрию. Первый технический опыт должен охватить две конкурентные попытки реза, поздний вход, разрез переносимого предмета и повторное разрезание фрагмента.

## 5. Жидкость и заполнение рта

Рекомендуется серверный игровой объём жидкости с уровнем в координатах рта и отдельное визуальное представление. Профиль события задаёт кривые наполнения/слива, направление и силу потока, температуру/статусы, время контакта до эффекта и следы после ухода жидкости.

Проверка погружения использует форму объёма и положение персонажа/физических тел. Сам факт нахождения в ограничивающем box не означает, что игрок под водой: учитывается поверхность. Твёрдые предметы получают настроенные сопротивление/плавучесть, стоящие персонажи — воздействие через движение, ragdoll — силы на физические тела. Сила не применяется одновременно обоими способами к одному персонажу.

Для первых четырёх волн кофе достаточно управляемой поверхности и движущихся областей воздействия, с маской внутри рта и фазами стока в глотку. Лёд создаётся отдельными физическими предметами. Статусы и остаточное загрязнение подтверждает сервер; источник события и ID применения не допускают бесконечного повторного начисления одного эффекта.

Niagara можно использовать для поверхности, брызг, пены и реакции на предметы. Epic описывает Shallow Water как поле высот, а 3D FLIP — как более затратную объёмную симуляцию. Для проекта предлагается сначала игровая модель уровня/потока, затем выбор качества эффектов по замерам. Игровой результат не должен зависеть от частоты кадров GPU-эффекта конкретного клиента. См. [Fluid Simulation Overview](https://dev.epicgames.com/documentation/unreal-engine/fluid-simulation-in-unreal-engine---overview).

## 6. Движение рта, зевание и хват

### Движущаяся арена

Предлагается отдельный `ArenaRoot`: к нему относятся движущиеся пол, зубы и границы рта. Событие задаёт кривые смещения/наклона и серверное время начала. Игровые коллайдеры движутся вместе с поверхностью. Свободная еда и ragdoll остаются физическими телами в мире; их нельзя просто прикрепить к корню и телепортировать вместе со всей ареной.

CharacterMovement должен корректно учитывать движущуюся опору. Якоря хвата, источники еды, зоны глотки и жидкость задаются относительно рта. Нужна проверка взаимодействия движущихся коллайдеров с захватом, телами и сетевой коррекцией. Основной ракурс камеры остаётся стабильным; дополнительная тряска камеры только поддерживает видимое движение.

### Зевание

Профиль зевания содержит фазы предупреждения, вдоха, перехода, выдоха и затухания. Вдох тянет к глотке, выдох действует в противоположную сторону. Сила определяется положением внутри рта, фазой и кривой события; фазы синхронизируются серверным временем.

`Grip` предлагается как отдельное состояние взаимодействия. Хват хранит ID зуба, локальную точку, расстояние и допустимую нагрузку. Сервер разрешает захват только доступного якоря в досягаемости. Для первого физического варианта корпус удерживается ограничением у опоры, руки визуально тянутся к точке. Более точное удержание каждой кистью можно развить после проверки базового хвата.

При исчезновении зуба, разрыве связи или отпускании хват освобождается с сохранением скорости. Одновременный хват двумя игроками и возрождение из удерживаемого зуба должны обрабатываться явно. Выносливость, число хватов на зуб и возможность хватать другого игрока остаются настройками/открытыми решениями GDD.

### Попадания едой

Твёрдые продукты спавнятся сервером над ареной, падают под гравитацией и передают движение клиентам. Hit-событие оценивает относительное движение в точке контакта и массу; профиль пищи задаёт влияние на персонажа. Для лёгкого касания используется толчок, для сильного — существующий вход в ragdoll. При ударе по уже упавшему герою импульс продолжает действовать, если правила защиты не запрещают его.

Нужны фильтрация контактов самого владельца, защита от многократного начисления одного попадания и проверка быстрых/маленьких предметов на прохождение сквозь коллизии. Энергия инструмента, загрязнение и урон здоровью — отдельные результаты контакта, их нельзя автоматически начислять одной универсальной формулой.

## 7. Переход от текущего прототипа

| Уже есть | Требуется для GDD 0.2 |
| --- | --- |
| `MouthHealth = 100`, семь дней | Статусы, конкретные причины урона и сохранение последствий |
| До четырёх сетевых игроков | Зубы арены как расходуемые жизни, правила гибели и возрождения |
| Проверки дистанции/видимости при работе | Контакт инструмента, циклы по 0,5 с и целочисленный прогресс |
| Случайный выбор одного типа задания | Меню, ротация завтраков и несколько фаз/событий в день |
| Упрощённые задания еды/ремонта | Физический захват, переноска, утилизация, полноценный ремонт и резка |
| Ragdoll и реакция на некоторые столкновения | Управляемая подача еды, попадания по лежащим, жидкость, зевание и движение опоры |
| F1 и DA анимации/физики/звуков | Редактируемые определения новых систем и виджет проверки событий |
| Очистка заданий при смене дня | Постоянные состояния зубов, грязи, еды и повреждений между днями |

В текущем `OnBodyHit` уже есть вход в ragdoll от движущегося физического предмета, но обработчик отказывается работать, когда герой не может действовать. Поэтому это заготовка для падающей еды, а не готовая система повторных ударов по лежащим. Новые системы должны использовать существующую серверную модель физики, а не создавать независимые результаты попадания на клиентах.

Предлагаемый порядок реализации после согласования: правила забега и статусы → контактные инструменты → пища/захват/утилизация → меню и расписание → жидкость/зевание/движение опоры → разрезы и тяга по надрезу → сохранение и полный семидневный прогон. Отдельный опыт с разрезом нужен раньше финальной подготовки моделей, чтобы проверить требования к геометрии.

## 8. Приёмка будущей реализации

- Четыре стартовых персонажа не расходуют восемь зубов арены; одновременное возрождение двух игроков не использует один зуб дважды.
- Разрушенный зуб перестаёт быть доступной жизнью; поздний клиент видит тот же состав арены.
- Четыре подтверждённых стука очищают кофе; промахи, повтор пакета и несколько коллайдеров не ускоряют работу.
- Статусы корректно применяются и к героям, и к зубам арены; одно событие не наносит повторный разовый урон.
- Одинаковый seed воспроизводит ротацию; сохранение не выбирает меню повторно и не выдаёт ресурсы ещё раз.
- Еда падает сверху, толкает стоящего и лежащего игрока; переносимый предмет и его части остаются согласованными у четырёх клиентов.
- Срез появляется в выбранной плоскости; обе части получают коллизию и физику; количество фрагментов ограничено.
- После разреза сохранение и поздний вход восстанавливают существующие части, их статусы и захваты.
- Уровень жидкости и фазы зевания совпадают у клиентов; отключённые эффекты не отключают игровое воздействие.
- Движение пола влияет на предметы; захват движущегося зуба и его исчезновение не оставляют персонажа зависшим.
- Переход дня сохраняет грязь, повреждения, лунки и остатки пищи; нагрузка не облегчается скрыто вопреки GDD.

Производительность, устойчивость сетевой физики и качество разрезов ещё не измерены для этих новых систем. Их нельзя считать проверенными на основании тестов текущего прототипа.

# MessControl — игровые системы

Актуализация: **23 октября 2026**. Техническая карта текущего исходного кода и границ реализации. Игровой замысел — в [GDD.md](GDD.md), устройство проекта — в [Architecture.md](Architecture.md).

**Статус доказательств.** «Реализовано» ниже означает наличие прочитанного C++ пути, а не успешный прогон текущей сборки. Анализ выполнен без изменения ассетов, сборки, cook, PIE и сетевых тестов. Выполнено узкое read-only чтение live clean объектов Editor: CDO BP_MouthGameMode, таблицы направлений Hub, DA_SingleDay и DA_RunRules; их результаты ниже отделены от native defaults. Это не свежий экспорт всех сохранённых пакетов и не подтверждение компиляции всех текущих source changes. Остальные saved defaults/rows не проверены; индекс ассетов требует обновления схемы/сборки. Граф `E-DEVGAME-MessControl` использован для навигации, затем проверены исходники. `check_index_coverage` показывает `metadata_changed`, а отражаемые UE-заголовки — `partial`; отсутствие ребра не доказывает отсутствие механики.

## 1. Владение игровым состоянием

| Владелец | Ответственность |
| --- | --- |
| `AMCGameMode` | Серверный запуск/сброс смены, выбор контура, создание зубов, участники, смерть/возрождение, очки |
| `AMCGameState` | Реплицируемые фаза, день, здоровье рта, правила, seed, зубы, ссылки на директоров и их состояние |
| `AMCSingleDayDirector` | Порядок крупных событий, порции, условия перехода, общие сундуки этапов |
| `AMCGameDirector` | Адаптивный допуск обычных событий по нагрузке; самостоятельные дни или поддержка между крупными событиями |
| `AMCDayDirector` | Прежний сценарий первого дня и переиспользуемые сервисы подачи/загрязнения |
| `AMCPlayerState` | Очки, перки, история выбора сундуков и экономика; переживает замену Pawn |
| `AMCToothCharacter` и компоненты | Ввод, движение, ragdoll, здоровье, инструменты, хват, стек пищи, взаимодействия |

Сервер подтверждает повреждение, очистку, доставку, награду и переходы. Клиенты получают состояния/серверное время и строят представление. Наличие репликации не доказывает исправность позднего входа или сетевой физики текущей сборки.

Источники: `Source/MessControl/Public/MCGameMode.h`, `MCGameState.h`, `MCPlayerState.h`; реализации с теми же именами в `Private/`.

## 2. Несколько существующих контуров

| Контур | Выбор | Завершение |
| --- | --- | --- |
| Авторенная последовательность SingleDay | `bUseSingleDayLoop`, `-MCSingleDay`, Hub destination с SingleDayProfile | После последнего слота остаётся бессрочная поддержка; штатный финал фрагмента не задан |
| Адаптивные дни | `bUseAdaptiveDirector`, когда SingleDay выключен | Дневной дедлайн, перенос текущих последствий, до седьмого дня |
| Авторенный первый день | `bUseDayOnePlan` в соответствующей ветке | Пошаговый `UMCDayPlan`; ранний сценарий |
| Прежние случайные задачи | `-MCLegacyDays` выключает адаптивную/первую сценарную ветку | Случайный `UMCDayEvent`, дедлайн, успех/штраф и следующий день |
| Учебная/ручная проверка | `L_Tutorial`, опции и dev-сценарии | Собственное завершение |

Native defaults в `MCGameMode.h`: `bUseSingleDayLoop=false`, `bUseAdaptiveDirector=true`, `bUseDayOnePlan=true`. Прочитанный live clean CDO `BP_MouthGameMode` имеет SingleDay=true/DA_SingleDay; в clean таблице Hub Day01 включён, ведёт в L_Mouth с DA_SingleDay, дни 2–7 выключены. Это отдельное editor-loaded evidence, не сборка текущего C++. `-MCCore`, `-MCDayOne`, `-MCLegacyDays` меняют выбор. Начало SingleDay ожидает Pawn и ACK загрузки участников; стадия `Training` и имя `BeginFirstPerk()` не означают повтор обучения или бесплатный перк: текущий путь начинает еду без стартовой награды. [Детали источников](ProjectAudit.md).

`RestartShift()` уничтожает текущую еду/сценарии, пересоздаёт персонажей и зубы, сбрасывает здоровье, seed, очки и награды. Это отличается от сохранения последствий через дневную границу. `?Seed=123` помогает повторять выбор контента, но не обещает побитовую детерминированность Chaos.

Источник: `Private/MCGameMode.cpp::BeginPlay/RestartShift/BeginSingleDaySequence/Tick/StartDay`.

## 3. Последовательность SingleDay

`UMCSingleDayProfile` хранит KeyEvents, варианты орехового события, порции, паузы и ориентир **25–35 минут**. Ориентир не является таймером победы. На старте создаётся копия профиля: нормализация и совместимость не сохраняют изменения в DA.

Новый native профиль: **NutEncounter → Jellies → IceEvent → FogBrawl**. Этот же порядок подтверждён в загруженном **`/Game/Gameplay/CoreLoop/DA_SingleDay`**, `is_dirty=false`; `bLegacyTimedFinale=false`. Ассет другого забега может задавать другой порядок. Совместимость старого массива из одного NutEncounter добавляет IceEvent, прежнего Nuts/Ice — FogBrawl; она не вставляет Jellies во все старые профили.

Узкое live clean чтение DA_SingleDay подтвердило следующие значения:

| Поле | Загруженное значение |
| --- | --- |
| OpeningMealPortions / AfterNutMealPortions | [3,5,8] / [5,8,9] |
| RunTargetMinMinutes / MaxMinutes | 25 / 35; ориентир, не victory timer |
| AfterTrainingPause / BetweenMealPause / BeforeNutsPause | 5 с / 5–10 с / 4 с |
| OpeningMealDrop / AfterNutMealDrop | 1 с / 1 с |
| DirectorSupportSeconds | 120 с у каждого из четырёх слотов; read path последнего слота не создаёт дедлайн |
| NutRainVariants | DA_NutRain в общем массиве и слоте NutEncounter |
| SmallMint | HP/player=180, diameter=135, fall=1.4 с/850 см, firstWave=3–5 с, rest=3–5 с, radius=2600, travel=2.8 с, footIceHP=80 |
| Legacy-поля | CompletionExperience=25 у слотов, DirectorSeconds=30, FinalBossClass=BP_ZombieBoss_C; наличие значений не включает XP или legacy finale |

Для этого чтения использованы `editor_toolset.toolsets.object.ObjectTools.list_properties/get_properties` и `editor_toolset.toolsets.asset.AssetTools.is_dirty` через `mcp__unreal_epic__call_tool`. Editor оставался в L_MainMenu, PIE=false. Clean loaded objects — узкое подтверждение этих значений, не полный fresh disk export и не проверка бинарников против всех текущих исходников. Числа ниже совпадают и с native defaults, и с прочитанным DA.

| Шаг | Текущий контракт |
| --- | --- |
| Готовность → пауза | Без бесплатного перка/XP; native пауза 5 с |
| Первый Relax | Native порции **3 → 5 → 8** целых продуктов для всей команды; weighted выбор обычной еды с WholeMeshes |
| Завершение порции | Всё подано; нет незавершённых акторов/угроз пищи; пол и доступные зубы чисты. Последняя порция проверяет пищу всего мира, не только batch |
| Награда порции | Общий выбор бустера блокирует следующую подачу. После непоследней порции — одна волна кофе, затем пауза 5–10 с от фактического конца волны |
| Переход к орехам | После последней порции/сундука — native пауза 4 с; дополнительный кофе не навязывается |
| NutEncounter | Дождь → Рыцарь → превращение в Колдуна; обычная поддержка остановлена |
| Специальный переход Nuts → Jellies | Второй Relax **5 → 8 → 9**, без случайных hazards/кофе; сундук после каждой чистой порции → малая мята → сундук → следующий слот |
| Прочие завершённые слоты | Общая награда, затем поддержка до следующего слота; native DirectorSupportSeconds=120 |
| Последний слот | `bAuthoredFragmentComplete=true`; поддержка без дедлайна. Автоматической победы через 25–35 минут нет |

Подача учитывает конвейер: целых продуктов меньше `clamp(6 + 2 × (живые работники − 1), 6, 12)`, фрагментов меньше 48, глотка не занята. После ограниченных неудачных попыток сценарий явно выставляет ошибку/поражение. Переносимая пища и незавершённая доставка остаются работой после окончания спавна.

Отдельный `bLegacyTimedFinale` возвращает старую цепочку с ограниченным interlude и зомби-боссом; его смерть даёт Won. Это совместимость короткого прототипа, не обязательный финал новой последовательности.

Источники: `Public/MCSingleDayDirector.h`; `Private/MCSingleDayDirector.cpp`, `MCSingleDayDirectorPostNut.cpp`, `MCSingleDayDirectorRewards.cpp`.

## 4. Адаптивный директор

`Observe()` измеряет существующий мир: целую еду, фрагменты, переноску/очередь глотки, грязь, ремонт, язвы, огонь, лёд, живых/доступных игроков, HP/stamina, глобальные движения и срочные угрозы. Работа оценивается в worker-seconds:

`Pressure = WorkSeconds / (max(1, AvailablePlayers) × 40) + 0.3 при глобальном движении + 0.35 при срочной угрозе`.

Throughput оценивается по исчезающей работе с фильтрацией напитков и срочных событий. HP, stamina, занятость и превышение давления влияют на Stress; Difficulty и TargetPressure плавно адаптируются. Масштабирование есть в коде, но баланс для 1–4 игроков здесь не проверялся.

Пул: Food, Coffee, CoffeeFlood, ColdCola, Yawn, Pepper, StuckFood, LooseTooth, Reward, Boss. Вес — вероятность допущенного события, не обязательная квота. Допуск проверяет cooldown, фазу Build/Drain/Rest/FinalCleanup, свободных игроков, прогноз давления, ёмкость очереди, занятый рот и наличие нужной строки/зуба/босса. Есть исход «ждать» и снижение повторов. Боссу нужен живой dormant actor; Reward — заработанная ожидающая награда.

Предупреждённый ticket резервирует окно, но перед стартом повторно проверяется и может отменяться. Отмена невыданного события не создаёт долг; существующие последствия остаются. Причины блокировки, вероятности и журнал реплицируются в `FMCGameDirectorState`.

`BeginSupport()` отключает случайные Boss/Reward и меняет runtime-копию настроек. Его таймер не завершает забег — очередным слотом владеет SingleDay; `Seconds=0` означает отсутствие дедлайна. В самостоятельном режиме `FinishDay()` штрафует остаток и переносит последствия. В нём зашито `Day>=7`, тогда как прежний GameMode использует `RunSettings.DaysToSurvive`: учитывать это различие при изменении числа дней.

Источники: `Private/MCGameDirector.cpp`, `Public/MCGameDirectorTypes.h`, `MCGameDirectorProfile.h`.

## 5. Здоровье и запас возрождений

Native `FMCRunSettings`: здоровье рта 100, семь дней, максимум четыре игрока, восемь зубов арены. Однако live clean **`/Game/Data/DA_RunRules`** (`is_dirty=false`) содержит MaxMouthHealth=100, DaysToSurvive=7, MaxPlayers=4 и **InitialArenaTeeth=12**. Поэтому восемь — только native fallback, не подтверждённая настройка этого DA. SingleDay выставляет Day=1 и DaysToSurvive=1 для своего контура. Фактически созданное число зубов ограничивается sockets/доступной геометрией; его в PIE здесь не измеряли. Пустая тестовая карта получает программную раскладку с выбранным числом зубов.

`UMCToothStatusComponent` хранит локальные HP/MaxHP, CoffeeLeft/CoffeeTotal, RepairLeft и timestamps реакций. Компонент общий герою и зубу арены, но уход различается. MouthHealth хранится отдельно.

Смерть помещает Pawn в очередь. `ProcessRespawns()` после задержки берёт доступный зуб с наименьшим ToothId, ищет свободное место внутрь арены, создаёт героя и только после успеха вызывает `ConsumeForRespawn()`. Отказ спавна не тратит зуб; повторная запись смерти не дублирует очередь. Наследование `bInheritReserveStatus` сейчас выключено в native defaults и `DA_ToothCare`: сменщик появляется чистым, без расшатывания и с полным HP. После possession сначала применяется максимум здоровья от перков, затем заполняется здоровье новой замены; обычное получение max-HP перка по-прежнему не лечит. Наследование статуса оставлено как отдельная настройка для возможного будущего режима. Класс старого Pawn, контроллер, открытый water jet/cooldown переносятся; перки остаются в PlayerState.

Поражение: MouthHealth<=0 либо есть участники, живых нет и доступных зубов нет. Нулевой запас при живом игроке не завершает забег. Технический отказ ключевого события тоже может выставить Lost; его следует отличать от игрового поражения.

Урон проходит серверные проверки и перки. Обычный прямой источник `AMCToothCharacter` не наносит HP-урон другому герою через `Damage`; специальные hazards имеют собственные правила. Ragdoll/толчок, потеря стека, личные HP, статус и MouthHealth — отдельные последствия.

Источники: `Public/MCRunRules.h`, `MCToothStatusComponent.h`, `MCArenaTooth.h`; `Private/MCGameMode.cpp::PlayerDied/ProcessRespawns`, `MCToothStatusComponent.cpp`.

## 6. Очистка и лечение

| Цель | Реализация |
| --- | --- |
| Зуб арены | Пространственная 3D GrimeMask; локальный мазок по реальной коронке, проверки направления/достижимости/видимости/готовности руки |
| Пятно языка | WipeMask и deposit mask; локальный 2D мазок по поддерживаемой поверхности |
| Герой | Непрерывный контакт; native ContactSeconds=0.5, CoffeeContacts=4. Уход за собой разрешается отдельной настройкой |
| Повреждённый зуб арены | Спрей по удерживаемому вводу; RepairWithTool восстанавливает HP и убирает расшатывание при полном ремонте |
| Герой с низкими HP | Базовый уход не лечит HP; восстановление перками отдельно |
| Язва/огонь | Непрерывные Treat/Extinguish по проверенной цели; лечебный watergun усиливает работу |
| Зубной камень | Отдельный UMCToothCalculusComponent: прикреплённые участки с дискретными стадиями скола, локальное разрушение киркой; Buffer-контакт сохранён, но upgrade отключён |

CoffeeLeft у пространственной грязи отражает оставшееся покрытие, а не четыре независимых удара. У коронки есть порог завершения тонкого остатка, у обычной лужи свой порог, у paint tiles проверяются мокрые ячейки. История worker/approach epoch/времени/расстояния не позволяет возобновлённому мазку стереть длинный мост между контактами.

`UMCBrushContactComponent` согласует цель, щетину, направление корпуса и кисть; пена следует контакту. Плавание в кофе блокирует обычную работу щёткой. Новый paint deposit добавляет лишь новое покрытие и не заливает уже вычищенную область от того же стационарного источника.

Зубной камень не является кофейной маской: seed, surface anchors и состояния кусков реплицируются отдельно. Кирка скалывает ближайший участок/окрестность; короткие осколки — пакетное представление без отдельных Chaos bodies. Сохранённый Buffer-код обрабатывает контактную сферу, но выдача/активация перфоратора сейчас запрещена eligibility/HasToolUpgrade. Native настройки зуба допускают небольшие начальные отложения, но фактическое назначение в карте требует проверки профиля.

Зубочистка — отдельная последовательность `Falling/Impaled → Extracted → Broken → wound healed`: сначала вытягивание, затем кирка, только после разрушения разрешается лечение её язвы. Рана следует поверхности языка; её специальная боль реагирует на шаг игрока, а учебная версия отключает урон. Это нельзя заменить обычной уборкой еды или четырьмя контактами щётки.

Источники: `Private/MCToothCharacter.cpp::FindCareTarget/UpdateCare`, `MCBrushContactComponent.cpp`, `MCArenaToothGrime.cpp::BrushGrime`, `MCMouthLiquid.cpp::BrushLiquid/AppendLiquidDepositMask`, `MCToothStatusComponent.cpp`, `MCInventoryComponent.cpp::TickComponent`, `MCToothCalculusComponent.cpp`, `MCToothpick.cpp`, `MCDamageUlcer.cpp`.

## 7. Инструменты, бой и переноска

Четыре слота: Brush, Pickaxe, Knife, Spray. Серверное переключение сбрасывает несовместимое действие/комбо. `UMCEquipmentProfile` задаёт меши, контакты/позы, reach, урон и watergun. Native урон кирки 40, ножа 25; сохранённые значения не подтверждены.

Нож обрабатывает мягкую еду, кирка — твёрдую; классификация задана Resistance или резервным именем. Бензопила допускает обычную еду независимо от этой пары. Доступные tool upgrades: мегащётка, бензопила, watergun; слоты сохраняют уборку/лечение. Buffer/перфоратор имеет сохранённые профиль/позы/контактный путь, но явно исключён в IsDefinitionUsable и HasToolUpgrade. Watergun: лечение и переключаемый автоматический огонь с магазином/перезарядкой; старые charge-поля только для совместимости.

Ближний бой использует серверные окна контакта, trace/sweep, дистанцию/видимость и контекст цели. Комбо, trail, feedback и реакции отделены от начисления урона: косметическая анимация сама не повторяет impact. Инструменты/боссы/hazards могут иметь специальные правила вместо общего Damage().

`UMCFoodCollectionComponent` собирает фрагменты/маленькие продукты в удерживаемый стек. Крупный целый овощ нужно обработать; при подборе его collision не уменьшается. Урон/сильный контакт может рассыпать стек. Tools и специальные hazards сохраняют отдельный `UMCGripComponent` с хватом, переноской и тягой. Обычные фрагменты не обязаны использовать прежнюю совместную Holders-переноску.

Источники: `Public/MCInventoryComponent.h`; `Private/MCInventoryComponent.cpp`, `MCInventoryAim.cpp`, `MCInventoryUpgrades.cpp`, `MCMeleeCombo.cpp`, `MCFoodCollectionComponent.cpp`, `MCGripComponent.cpp`, контактный путь `MCToothCharacter.cpp`.

## 8. Конвейер пищи и сортировка

`FMCFoodRow` задаёт WholeMeshes/FragmentMeshes, независимые масштабы, baked collision data, массу, HP, сопротивление, вес, число частей, свежесть и hazards. Свежесть ведётся от абсолютного SpoilAt; переноска не обнуляет его, но перк может менять скорость порчи.

`HitFood()` снижает HP целого продукта; при нуле `SpawnFragments()` создаёт акторы из заранее подготовленных FragmentMeshes. При успехе оригинал утилизируется, части остаются для доставки. Обычный фрагмент от следующего удара толкается без рекурсивного дробления. **Разреза геометрии по плоскости инструмента здесь нет.**

Enum Absorbing не означает активное растворение: старые методы в `MCFoodAbsorption.cpp` оставлены пустыми. Обычная испорченная еда не создаёт язву автоматически. Целые физические продукты могут повреждать/сбивать героев; обычные фрагменты не атакуют игроков через OnHit.

Свежая пища предназначена глотке, мусор/испорченное — переднему выходу. В manual-intake глотка принимает реально брошенный предмет без носителя через входное отверстие; Q выполняет бросок с прицеливанием. Сохранена и прежняя автоматическая передача у delivery zone, включая снятие слоя стека; активная настройка сохранённого actor не подтверждена.

`AMCThroat` ведёт очередь, anticipation, глоток, всасывание, спазм и рвоту. Дедлайн принадлежит первой доставке и не продлевается товарищами. Неподходящая пища вызывает соответствующие последствия; tutorial обрабатывает ошибку безопасно. Передний `AMCFoodDisposal` не засчитывает свежую пищу как мусор.

Чили остаётся бросаемым hazard: обычный удар не режет его и не сбрасывает fuse; взрыв оставляет специальные угрозы. Завершение проверяет `IsHazardResolved()`, не только Disposed. `MCMeasureFoodPipeline` объединяет еду, части, переноску, транспорт/глотание, unresolved hazards и остаточную работу для директоров.

Источники: `Public/MCDayPlan.h`, `MCFoodActor.h`; `Private/MCFoodActor.cpp`, `MCFoodEnvironment.cpp`, `MCFoodAbsorption.cpp`, `MCSpicyFood.cpp`, `MCThroat.cpp`, `MCFoodDirectorHooks.cpp`.

## 9. Язык, напитки и движение

`AMCTongue` использует общую топологию ProceduralMesh для видимой поверхности и треугольной Chaos collision. Deformation, pressure loads и motion state представлены отдельно; это физическая опора, а не только camera shake. SurfacePoint, rest-поверхность и gameplay footprint переиспользуются для еды, грязи и безопасного спавна.

Зевание — воздух к глотке с сохранением ввода/удерживаемой пищи. Старые автоматические hand/foot anchors убраны. Brace/grip не означает автоматическое приклеивание игрока во время зевания. Полный цикл вдох/пауза/обратный выдох из старого проекта не является текущим контрактом.

CoffeeFlood/CoffeeProfile задают Fill/Hold/Drain, циклы, поверхность, течение/сток, плавучесть, сознательное плавание и ragdoll. Напиток оставляет грязь. Циклы читаются из coffee profile, старый DayPlan.WaveCount — legacy. SingleDay ограничивает принадлежащую порции волну одним циклом runtime-копии без сохранения в DA. ColdCola с холодом/льдом — отдельная система от крупного IceEvent.

Новые runtime-материалы/эффекты должны быть достижимы из загрузочного/prewarm manifest. Тёплый Editor cache не проверяет packaged PSO или первый показ текущей сборки.

Источники: `Public/MCTongue.h`, `MCTongueProfile.h`, `MCCoffeeProfile.h`; `Private/MCTongue.cpp`, `MCTongueMotion.cpp`, `MCTonguePressure.cpp`, `MCTongueSpawn.cpp`, `MCYawn.cpp`, `MCCoffeeFlood.cpp`, `MCColdCola.cpp`.

## 11. Награды, перки и очки

XP/team level-up **выключены**. `UMCProgressionComponent` — совместимая оболочка: AddExperience→0, требуемый XP=0, HasPendingChoices=false. TeamLevel/CompletionExperience и старые widgets/поля не означают действующую экономику опыта.

SingleDay выдаёт общий stage chest за чистую порцию/этап. Проверяется центральное место видимого языка. Первый допустимый подошедший игрок выбирает из **фиксированных ID**, перемешанных по seed: `Fallback_Mouthwash`, `Fallback_BrushFury`, `Fallback_Grenade`. Один выбор сразу действует на живую команду; это не три случайных личных перка. Stage chest не становится mimic; следующий этап ждёт, уничтоженный незабранный сундук повторяет попытку появления. Требуются все три положительные booster-строки DT_Perks; их текущая полнота не проверена.

Mouthwash выполняет общий эффект один раз по объединению радиусов, Fury задаёт временное состояние, Grenade вооружает срабатывание при knockdown. CompletionId/ClaimedMask/серверный guard защищают от дублирования.

Отдельный `AMCRoguelikeDirector` поддерживает очередь earned rewards, зоны падения, личные offers, polarity/rarity, tool upgrades, risky altar/cursed contract и mimic. Его API не доказывает выдачу всех вариантов каждым этапом SingleDay. Перки находятся у PlayerState, поддерживают stacks/условия/EffectClass.

Очки вклада отделены от XP: native Coffee=10, Repair=20, Food=5, Ulcer=25, Ice=10. Tutorial/lobby не начисляют их; доставка и завершение защищены от повторного credit.

Источники: `Private/MCProgressionComponent.cpp`, `MCSingleDayDirectorRewards.cpp`, `MCStageBoosterRewardChest.cpp`, `MCRogueBoosters.cpp`, `MCRoguelikeDirector.cpp`, `MCRogueOffers.cpp`; `Public/MCPerkTypes.h`, `MCPlayerState.h`.

## 13. Проектные направления и следующая приёмка

Полезные идеи прежнего SystemsDesign/GDD 0.2 сохранены как **планы**:

- Настоящий разрез требует геометрии, закрытого сечения/cap material, collision частей, лимитов и сетевого снимка/истории операций. Разрыв тягой по надрезу — отдельная задача деформации/прочности.
- Составные меню и shuffle-bag ротация без непосредственных повторов — развитие текущего weighted выбора строки: нужны fallback, seed/history и восстановление.
- Универсальные DT_StatusDefinitions/UMCStatusComponent старого проекта не являются действующим общим framework; фактически работают специализированные системы.
- Полный save требует Day/Stage, конкретных зубов, HP/статусов, масок, еды/частей, активных фаз, перков, seed/выборов и выданных наград без повторного начисления после загрузки.
- Для многодневной версии остаются лунки, заживление, финал и reconnect. Их нельзя выводить из enum или старой таблицы дизайна.

Следующая проверка: подтвердить оставшиеся saved assignments и соответствие бинарников текущим source changes; по явному запросу собрать актуальную сборку; затем короткий solo check выбранной механики. Сетевые прогоны, полное прохождение и Windows package — отдельные задачи. В этой актуализации проверены исходники/граф/coverage и узкие clean загруженные CDO/table/DA через Unreal MCP; gameplay runtime, производительность и первый показ ресурсов не проверялись.

# Рогалик: навыки, пассивные эффекты и награды

Дата: **27.10.2026**. Редакция: **0.2**.

Статус: **функциональная основа реализована** в исходниках и сохранённых Unreal-пакетах. Общая проверка native: 31 тест, 30 без предупреждений, один с предупреждением тестовой геометрии, ошибок нет. В owned solo PIE проверены HUD, заряды, независимые cooldown, личная награда и подтверждённая замена занятого слота; отдельная проверка хаба подтвердила E, покупку на следующий ран и стабильность витрины. Полный набор новых эффектов с пользовательских схем и финальный арт не реализованы в рамках основы.

Это актуальная точка входа для изменения правил. Общий каталог, выдача наград, покупки, ввод и HUD следуют одному контракту. Старый технический справочник — [Roguelike.md](Roguelike.md); статус общих проверок — [Validation.md](Validation.md).

## 1. Принятая и реализованная модель

| Часть | Правило |
|---|---|
| Активные навыки | Четыре слота на `1 / 2 / 3 / 4` |
| Расходники | Занимают те же четыре слота; `2/3` в исходном референсе обозначают заряды |
| Пассивки | Отдельный набор бафов, без жёсткого ограничения количества |
| Совместная работа пассивок | Разные ID работают одновременно; один ID не даёт усиления ×2/×3 |
| Инструменты | Колесо переключает инструменты. Редкая версия заменяет соответствующий стандартный инструмент по существующей механике |
| Источники редких инструментов | Магазин и сундуки; активные слоты и набор пассивок не расходуются |
| Слот-машина / гриль | Новые роллы выдают только монеты |
| Интерфейс | Функциональные индикаторы текущего HUD; полный визуальный дизайн — отдельная задача |

Прежнее предложение «четыре общих слота для пассивных и активных» отменено. Восемь пассивок и ориентир «четыре из хаба + четыре за ран» относятся только к компоновке HUD, а не к лимитам получения.

## 2. Общий каталог

Сохранены путь **`/Game/Gameplay/Roguelike/DT_Perks`**, структура **`FMCPerkDefinition`** и все **98 исходных ID**. Две технические записи довели каталог до **100 строк**. Второго независимого каталога определений навыков нет.

| Поле | Назначение |
|---|---|
| Имя строки | Стабильный ID для состояния игрока, наград, магазина и UI |
| `bEnabled` | Доступность записи; выключенная запись не предлагается и не выдаётся |
| `Kind` | `Passive`, `Active`, `Consumable`, `ToolUpgrade`; `Automatic` — совместимость прежних строк |
| `DisplayNameKey`, `DescriptionKey` | Ключи общей локализации; `DisplayName` / `Description` остаются текстовым fallback |
| `Icon`, `Category`, `Rarity` | Общая презентация, категория и редкость |
| `InitialCharges` | Начальное число зарядов расходника |
| `CooldownSeconds` | Независимая перезарядка конкретного активного предмета |
| `ActivationAdapterID` | Необязательная ссылка на уже реализованное действие; пустое значение использует собственный ID |
| `EffectClass`, `Modifiers` | Расширяемое поведение и параметры; текст описания не исполняется как игровое правило |
| `RequiredTool`, `RequiredEvents`, `bRequiresTeam` | Проверки доступного контекста |
| `ToolUpgrade`, `ChoiceFamily`, `Weight` | Связь с улучшением инструмента и параметры выборки |

При `Automatic` сначала определяется улучшение инструмента, затем расходник по прежнему флагу `bConsumableBooster` или известному recovery-ID; остальные строки считаются пассивками. Новые строки следует типизировать явно. Старое поле `MaxStacks` сохранено для совместимости пакетов, но не разрешает повторное владение ID или уровни одной пассивки.

Магазин хранит отдельно цену и настройки витрины, ссылаясь на общий ID. Названия, описания, иконки и вид навыка читаются из `DT_Perks`. Вероятности и цены текущих примеров — тестовые значения, а не утверждённый баланс полного нового каталога.

### Технические примеры

| ID | Реализованное поведение |
|---|---|
| `Active_BrushFury` | Повторно используемый активный «Щёточный вихрь»: существующее действие длится 5 секунд, cooldown — 15 секунд; адаптер `Fallback_BrushFury` |
| `Consumable_RepairKit` | «Запасные пломбы»: 3 применения по 25 HP, cooldown — 1 секунда; адаптер `RecoverySelfHeal`. При полном HP применение отклоняется без расхода заряда |

Это проверка инфраструктуры на существующих действиях. Она не означает реализацию всех пассивок, гранат, ракетницы, машины и других эффектов с пользовательских схем. Повтор «Свежая доставка» на исходной схеме остаётся одной будущей записью, пока не заданы два разных эффекта.

## 3. Владение, слоты и применение

Состояние находится в `UMCPerkComponent` на `PlayerState`:

- `ActiveSkillSlots` — ровно четыре места для активных навыков и расходников;
- `PassivePerkIDs` — уникальные пассивные ID, без ограничения восемью;
- `OwnedToolPerkIDs` — отдельная принадлежность улучшений инструментов.

Пассивки из разных источников сосуществуют. Категории «Бой», «Выживание», «Еда», «Уборка», «Спрей» не образуют дополнительные слоты. Числовые ограничения существующих модификаторов сохраняются; отсутствие лимита количества ID не отменяет ограничения конкретных характеристик.

Каждый занятый активный слот хранит `PerkID`, `InstanceID`, оставшиеся `Charges` и `CooldownEndsAt`. Повтор исключается только пока ID принадлежит текущему набору игрока. Заменённый предмет снова может выпасть. Последний успешно использованный заряд освобождает слот, после чего ID снова доступен.

Активация проверяется на сервере: принадлежность PlayerState/Pawn/Controller, живой и способный действовать персонаж, рабочая фаза рана, отсутствие блокирующего интерфейса и действующий instance слота. Простое получение предмета не применяет его эффект. При неготовом cooldown, полном HP для известного лечения или неподдержанном действии заряд не расходуется.

`UMCPerkEffect` предоставляет `CanActivate`, `OnActivate` и `CancelActivation`. Базовая реализация отвергает неподдержанное активное действие. Пассивный `OnApplied` не используется как универсальная активация. Полная подготовка, прицеливание и бросок каждой будущей гранаты требуют отдельной реализации; текущие hooks не означают готовность этих механик. Отмена подготовки не возвращает уже принятые заряды и не сбрасывает cooldown.

`ActivePerks` и `BoosterQueue` оставлены как совместимые представления канонического состояния. Старые команды выдачи больше не обходят четыре слота и не активируют полученную награду немедленно.

## 4. Получение, замена и таймер

Сундук и применение подготовленных покупок используют общие серверные проверки. Для активного предмета:

1. При свободном месте предмет устанавливается в слот.
2. При четырёх занятых местах игрок выбирает заменяемый слот либо пропуск.
3. До подтверждения сохраняется старый набор; покупка не списывает монеты преждевременно.
4. Замена требует совпадения текущего ID и `InstanceID` заменяемого предмета. Возврат такого же ID после предыдущей замены не делает старый запрос действительным.
5. Пакет выдачи целиком проверяется до изменения состояния; неприемлемая запись не оставляет половину покупки или сделки.

У каждого игрока личный набор карточек и личный исход выбора. Открытое предложение сохраняется: переоткрытие панели и смена зубика не дают бесплатный реролл. Завершение выбора одного игрока не закрывает карточки остальных. Один или два подходящих предмета образуют допустимое предложение; нулевой пул завершается пропуском.

40-секундный срок этапного сундука не продлевается при выборе места замены. По истечении срока допускается прежний автовыбор только из уже выданных вариантов, которые принимаются **без замены**: например, пассивка или активный предмет при свободном месте. Если безопасного варианта нет, выбор пропускается, старые слоты сохраняются. Полный активный набор никогда не заменяется случайно.

Пассивка добавляет отдельный баф. Инструмент идёт в существующую замену оружия. Сохранена прежняя принадлежность улучшений: командная выдача legendary-инструмента из сундука не превращает личную покупку в командную.

## 5. Магазин, гриль и сохранение

Магазин предлагает пассивки, активные навыки, расходники и редкие улучшения инструментов. Случайная витрина с весами редкости фиксируется на ран: повторное открытие, смерть и восстановление состояния не дают бесплатный реролл. Следующий ран обновляет витрину. До четырёх пассивных позиций — ограничение витрины, а не количества бафов или покупок.

Покупки хаба готовятся к ближайшему рану. План будущих активных предметов имеет свои четыре места и защиту подтверждения замены. Пассивки не используют эти места. Проверки будущей покупки учитывают подготовленный набор; при фактической выдаче в ране общий core проверяет итоговый контекст.

Смерть и смена зубика сохраняют навыки, заряды и оставшееся время cooldown. Перенос между мирами пересчитывает оставшийся срок относительно часов новой карты. Завершение рана сбрасывает навыки, монеты остаются. Постоянное владение навыками не вводится.

Миграция старой очереди покупок сохраняет оплаченные предметы: каждая прежняя запись расходника означает ровно один заряд, а не новую полную упаковку. Неизвестные или пока не помещающиеся записи не обрезаются молча и остаются ожидающими с сообщением. Новое сохранение отделяет подготовленные покупки от прежней очереди.

Гриль выдаёт монеты. Известные старые предметные receipts переводятся в соответствующий монетный результат; неизвестный receipt сохраняется для разбирательства вместо скрытого удаления. Остальные постоянные покупки и косметика не превращаются в расходуемые навыки.

## 6. Интерфейс и ресурсы

Текущий HUD отображает четыре активных состояния с цифрой, иконкой, готовностью/cooldown и зарядами, а отдельно — пассивные бафы. Полный новый арт, окончательная раскладка и motion-дизайн отложены.

Карточки сундука и магазина различают пассивку, активный предмет и инструмент. В модальном выборе цифры обслуживают интерфейс, а не запускают навыки за панелью. Колесо остаётся переключением инструментов; старые цифровые привязки инструментов сняты. Общая кнопка старой FIFO-активации не заменяет адресные слоты.

Иконки, brushes и ресурсы технических записей включаются в manifest подготовки использующей их локации через отражённые ссылки каталога/темы и существующие roots. Первое отображение известных карточек не должно впервые загружать их визуал. Само наличие этих ссылок не доказывает отсутствие PSO/streaming-задержек на чистом packaged-запуске; такой запуск в текущую проверку не входит.

## 7. Проверка

Сборка `MessControlEditor`, авторинг общего каталога и сохранение связанных данных выполнены. В `NativeFinal/index.json` получено **31 завершённое испытание: 30 Success, 1 Success с предупреждением, 0 Failed, 0 NotRun**. Предупреждение относится к CPU access тестового `Plane`, а не к ошибке приобретения навыка.

Проверки охватывают уникальные пассивки и отсутствие лимита восемью, четыре активных слота, strict replacement и устаревший instance, заряды/no-op, независимые cooldown и перенос между часами миров, отдельные карточки/таймаут, подготовленные покупки и миграцию, стабильность витрины, монетный гриль. Старые проверки same-ID stacks и мгновенного recovery переписаны под новый контракт.

Локальный машинный отчёт финальных бинарников: `E:/CodexWork/MessControl/RoguelikeFoundation_20261027/NativeProof/index.json`. Генерируемые отчёты и медиа не добавляются в Git автоматически.

**Solo завершена.** Arena `Solo9/Report.json` подтверждает четыре слота, девять разных пассивок, 3→2 заряда, отдельный cooldown, нормальный personal chest, отсутствие замены до подтверждения и фактическую замену выбранного слота с сохранением соседних зарядов. Hub `HubShopSolo2/Report.json` подтверждает E/ESC, одну оплату, next-run подготовку и тот же ассортимент после переоткрытия. Это изолированные диагностические fixtures (награды/кошелёк/позиция), не полноценное прохождение. Новые ссылки на иконки проходят через общий DT в prewarm; логи первого видимого применения сохранены. Финальный арт/motion не утверждены. Сеть, реальная передача микрофона, cook/package, реальный файловый рестарт legacy-профиля и чистый packaged first launch не проверялись.

## 8. Следующая итерация

1. Добавлять утверждённые эффекты со схем в тот же каталог, не создавая параллельный источник правил.
2. Для каждого нового активного предмета определить момент принятия действия, подготовку/отмену, cooldown/заряды и условия no-op.
3. Настроить редкости, веса, цены и сочетания разных пассивок на основе плейтеста.
4. Отдельной задачей разработать окончательные карточки, иконки, HUD и анимации. Ранее отключённый кальций сам по себе этой основой не включён.
5. При необходимости расширить историю происхождения навыка: общий список пассивных ID пока не является полноценным журналом «источник/ID выдачи/ран».
